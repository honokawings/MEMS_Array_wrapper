# 2026-09-17 首次上板网络与启动诊断

本次为实机网络观察及现有RTL/下载记录分析。尚未读取FPGA内部逻辑分析仪，也未测量板上引脚波形，不能据此断言某一个PLL、MDIO或RGMII模块已经损坏。

## 当前结论

完整系统首次测试时，电脑与板端PHY之间已建立千兆链路，但电脑没有收到任何有效的板端以太网帧。用户确认：实际闪烁的是板上丝印LED3，按住KEY0也不停止；KEY1按下时LED1不亮。因此不能把该闪烁认作本设计的音频心跳。

**后续IO诊断已实板通过：** 用户确认直接映射版、流水识别版的五键和五灯均按表对应。KEY0→LED0、KEY1→LED1、KEY2→LED2、KEY3→LED3、KEY4→LED4。按键/LED编号、基础接线与功能不再作为首要疑点，不应交换这些引脚。D18参考时钟能驱动流水逻辑，但其准确频率以及完整系统的96/122.88/125 MHz时钟仍未实测。证据见 [IO诊断记录](../../log/io_map_diag/board_observation.json)。

下一步优先在独立27 MHz参考域观察完整系统的三个PLL锁定信号、音频/网口计数器、KEY0原始电平及复位释放；再观察PHY管理器的状态、MDIO回读和重试。LED3的原有闪烁在正常模式下对应内部`link_up`状态，仍须结合内部信号确认，不能据此直接认定为PLL故障或MDIO故障。

已核对磁盘上的自测位流SHA-256与发布记录一致：`890f36447042e3bd278de8382c69a68c301aff41aadf33f2c2a8a6d34c1f9d62`。下载日志明确记录选择了该`.sbit`，多次Program成功且DONE=1；最近一次完成时间为22:46:24。用户说明是在JTAG下载后直接观察。因此没有依据把问题简单归为“选错旧文件”或“断电后Flash加载旧版本”；这也不是运行中配置的完整回读验证。

## 按键、LED和启动时间的关键矛盾

已同时核对硬件手册第34～35页的电路图/引脚表、当前FDC及实际布局布线端口表：

| 信号 | FPGA管脚 | 当前RTL含义 |
|---|---|---|
| KEY0 | C22 | 低有效全局复位，按下应复位PLL和数字逻辑 |
| KEY1 | C23 | 低有效；20 ms稳定按下后切换自测 |
| LED0 | A20 | 音频域心跳，每0.5秒翻转 |
| LED1 | C19 | 自测模式；不依赖网线、ARP或PCM成功 |
| LED2 | C18 | 本地自测数值通过 |
| LED3 | E18 | 正常模式为PHY管理器报告的link_up；自测模式为发送计数通过 |
| LED4 | A17 | 自测模式下的锁存故障 |

LED0的计数器由`audio_rst_n`复位，复位释放依赖`reset_n && lock_96 && lock_audio && lock_eth`。它不是只检测音频PLL，也不等待PHY链路、ARP、PDM启动或滤波稳态。KEY1到LED1同样只依赖该音频时钟/复位域。

若当前观察的LED3确实对应E18且系统处于正常模式，它闪烁意味着内部`link_up`闪变；这与电脑端持续1 Gbps的观察不同，应该读取MDIO状态与PHY管理器重试状态。若实物LED编号与手册不同，则上述解释不成立，须先做IO对应验证。

每次JTAG Program日志耗时约8.0～8.2秒。这可以解释从点击Program算起的一大段等待，不能解释DONE=1之后仍等待十几秒。正确的测量起点应为配置完成/DONE，而不是点击下载；随后分别记录PLL锁定、复位释放、LED0第一次翻转时间。

KEY0按下不影响闪烁是重要线索：需先确认按下的确为用户KEY0及C22输入确实变低。即使PHY对端网卡灯在复位时短暂保持亮，也不能替代FPGA端复位观测。另需确认闪烁LED属于核心板还是底板的用户LED，数字丝印本身不能证明网名相同。

## 建议的调试顺序与判据

### 1. 基础IO验证（已通过）

下面方案已通过独立诊断位流完成，用户确认两版五键五灯均符合预期。下一步从第2项时钟与复位开始；以下保留原检查方法供复现。

在底板测试点/按键焊盘测量KEY0、KEY1的释放和按下电平，预期约3.3 V与0 V。结合实物版本原理图确认其到C22/C23的连通关系；同样确认LED0和LED3分别连接A20/E18。无需直接探测BGA焊球。

下一版诊断位流应独立于音频/以太网PLL、PHY及DSP，以27 MHz参考时钟驱动用户LED轮流点亮，并直接观察同步后的各按键电平，同时显示构建标识。该版本用于实测按键和LED对应关系。不要在确认映射前盲目互换两个引脚，也不要通过关闭防火墙尝试修复按键无响应。

### 2. 再验证时钟与复位

2026-09-18 已收到实测：27 MHz 心跳从下载成功后约 0.5 秒开始、每 0.5 秒翻转；默认页 `1100`、频率页 `1110`；KEY0 可以被正确读取且观察域不受影响，但公共及两个局部复位仍未释放。以太网 PLL 未锁定，分频器因此保持复位。进一步检查安装的官方 PLL IP 校验脚本，发现旧以太网 PFD=125 MHz 与 OPTIMIZED 带宽不符合其 10～40 MHz 组合限制。下一步改为 PFD=31.25 MHz、输出比例不变，并使用 [UART 诊断](../../fpga/diagnostics/uart_clock/README.md) 经 COM3 反馈。不能把旧历史页 `0000` 当成启动正常，也不能把“松 KEY0 后恢复 0.5 秒”解读为系统复位已释放，因为用户未说明该时间对应哪个信号，且复位页明确为 `0000`。

上版独立诊断位流见 [验证步骤与 LED 页表](../../fpga/diagnostics/clock_reset/README.md)。69 项仿真、18 个引脚及快/慢角时序检查通过，发布证据在 `fpga/build/CLOCK_RESET_DIAG/release.json`。其板上反馈已定位到上述以太网 PLL 锁定失败。后续按用户要求，反馈和控制均改用 UART。

在27 MHz参考域记录三个PLL的锁定状态、失锁次数、复位次数，以及音频和网口域计数器是否递增。保留一个不依赖PLL锁定的诊断入口，避免故障发生时连观测灯也被清零。

预期音频时钟为122.88 MHz、网口逻辑时钟为125 MHz；实际频率须用适当仪器或跨域计数测量。仅凭某个LED闪烁不能证明这些频率正确。当前外部3.072 MHz麦克风时钟受采集使能和`link_up`控制，没有PDM时钟也不等于音频PLL未运行。

### 3. 读取PHY管理过程，而不只看网口灯

以125 MHz域逻辑分析仪观察：`phy.state`、`phy.cfg_step`、`phy_address`、`transaction_ack`、`transaction_data`、`phy_ready`、`phy_fault`、`link_up`、`RSTN_OUT`及MDIO收发方向。

重点判据：

- 复位释放后，PHY管理器应先完成约20 ms低电平复位、50 ms等待，再执行扫描及配置。
- PHY ID读回应为当前设计匹配的`0x001c / 0xc916`；无ACK、全1或全0要先查MDIO/MDC电平、复位和地址。
- 把配置失败的`cfg_step`和原始读回值保留下来，区分扫描不到PHY与某项寄存器回读失败。
- 当前通过page `0x0a43`、reg `0x1a`轮询，判断式为`(value & 0x003c) == 0x002c`。必须记录实板原始值，不能仅凭网卡协商到1 Gbps推断这个表达式已成立。
- 正常MDC约0.992 MHz；如果`RSTN_OUT`每约1秒重新拉低，说明发生初始化/访问失败重试，应追溯失败步骤。正常轮询约每10 ms一次。

### 4. 最后定位数据与RGMII

先看`calibration_done`、`acquisition_run`、`eth_stream_rst_n`。采集与发送流复位释放要求全局复位释放、校准完成且内部`link_up=1`。

| 内部观测 | 下一步 |
|---|---|
| `link_up=0`、流一直复位 | 先修PHY管理/复位问题，不调滤波器 |
| `link_up=1`但`calibration_done=0` | 检查128次校准握手与`cfg_ready` |
| 流已启动，PCM或包未产生 | 查`started`、`pcm_valid/ready`、FIFO和packetizer |
| `packet_full=1`、`peer_valid=0` | 应周期性发起ARP；检查`gmii_tx_en`和MAC状态 |
| `gmii_tx_en`有ARP突发但PC无有效帧 | 转向ODDR输出、TXC/TXCTRL/TXD、PHY RGMII延迟、幅度/边沿/相位测量 |
| PC看到FPGA主动ARP，回复后仍无UDP | 查RGMII接收、`rx_dv/rx_er`、ARP解析和`peer_valid` |

逻辑分析仪应按音频域和网口域分别采样，状态跨域要同步；不要用单一异步采样结果判断125 MHz数据有效性。外部测量重点是G16的125 MHz TXC、D20的TXCTRL，以及MDC/MDIO/PHY复位。

现有发布记录中的TXC抖动保守敏感性未通过，确实需要实测；但当前没有证据证明它就是本次根因，也不能用它解释KEY0/KEY1观测与RTL不符。先建立IO和内部状态的可信观测，再判断是否需要调整RGMII实现。

## 2026-09-18 UART 实板验证通过

用户确认下载 `CLOCK_UART_PFD31/uart_clock_diag.sbit` 后，通过 COM3、115200 8N1 自动采集 30 秒并发送 `r/t/t/c/s`。收到 125 条完整记录，帧号 102～226 连续；打开串口时另有一个上一帧的尾部片段。无丢帧、会话重启或 FPGA 串口接收错误。

三个 PLL 锁定、公共/音频/以太网复位释放、四路频率合格。原始 125 MHz、96 MHz、音频及以太网逻辑时钟的相对估计分别约为 125、96、122.88、125 MHz。124 条记录正常，唯一异常记录是主动执行 `r` 时的预期复位；此时 `lock=000 rst=000 now=F reset=1`，UART 与观察域计时保持运行。128 ms 后的下一条记录已恢复 `lock=111 rst=111 freq=1111 now=0`；这只给出采样覆盖的恢复上界，不能当作精确锁定时间。自检模式开启和关闭、清除/查询回执、音频心跳翻转均通过检查，全程历史故障为 0。

结合官方 IP 参数校验与旧版实测，证据支持原以太网 PLL 的 PFD/带宽组合错误导致其未锁定，并使依赖三路 LOCK 的公共复位持续有效；修正参数后，独立诊断中这条故障链已解除。五键五灯映射此前已通过，因此当前没有重新调整 IO 映射的依据。

本次采集开始于 FPGA 观察域运行约 25.5 秒，未覆盖配置完成后的首次启动；未验证断电重启、长期运行或完整系统网络。当前诊断固定 PHY 复位和麦克风时钟为低，不能用于判断 ARP/UDP 是否修复。下一阶段应将已验证的 PLL 参数合入带 UART 反馈的完整系统，先记录 PHY 复位、MDIO ACK/ID/配置步骤及 link_up，再抓取 ARP 和 UDP；在此之前，原完整系统位流仍保留旧 PLL 参数。
